# P0.6A Anthropic Native Lane (offline wiring notes)

Research/audit infrastructure only. **No live provider request was made during P0.6A.** This
slice adds an isolated Anthropic native probe lane (`anthropic-native`) that deliberately
preserves Anthropic Messages API semantics to challenge OpenAI-shaped assumptions (DevSpec
Section 50). Everything here is offline evidence produced by an injected fake that returns real
Anthropic SDK objects; real Claude behavior remains `unverified_until_live`.

## 1. SDK package and version (checked 2026-07-13)

- `anthropic==0.116.0` (released 2026-07-02), pinned in `probes/anthropic-native/uv.lock`.
- Python `>=3.13`. No `openai` or `langchain` package is pulled transitively — clean isolation.
- Versions were resolved by `uv` against PyPI and confirmed by introspecting the installed SDK,
  not copied from prior reports.

## 2. Selected direct API

`anthropic.Anthropic().messages.create(...)` — the direct Messages API (synchronous). Streaming
uses the same call with `stream=True`, yielding native `Raw*Event` objects. The Anthropic
OpenAI-compatibility layer is NOT used; no Bedrock, Vertex, OpenRouter, or custom `base_url`.

## 3. Retry and timeout ownership

All automatic retries disabled and proven, never assumed zero from configuration alone:

- `anthropic.Anthropic(max_retries=0)` — the SDK default is 2; overridden to 0. Verified the
  constructed client reports `max_retries == 0`.
- HTTP transport retry is owned by that same client setting.
- Probe retry: none. Harness retry: none. Subprocess retry: none (one fixture, one invocation).
- Timeout is owned by the client (`timeout=timeout_ms/1000`); the probe records
  `retry_count_observed` measured from the injected fake's call count (0 across all six).

## 4. Fixture coverage

The P0.6 base control set only: GEN-001, ROLE-001, STR-001, TOOL-001, STREAM-001, USAGE-001. No
stress, parallel-tool, cancellation, retry, embedding, or multimodal fixtures.

## 5. Raw evidence format

The probe writes a native request artifact (`anthropic_request.json`) and a response envelope
(`anthropic_response.json` / `anthropic_events.json` / `anthropic_error.json`) before any
normalization. Preserved native evidence includes: message id, requested model, provider-
returned model (on the message), message type, content-block order and types, text content,
tool_use id / name / raw input, stop_reason, stop_sequence, input/output token usage, cache
creation/read tokens when present, native stream event types and order, exception type + cause
chain + status_code + request_id, timing, and the anthropic package version. The requested
model is on the manifest; the provider-returned model stays on the raw message — kept separate.

## 6. Content-block semantics

Anthropic's shape is preserved, not reshaped into OpenAI forms:

- The system instruction is a TOP-LEVEL `system` field. No assistant/system message is invented.
- Each message `content` is a native content-block list (`{"type":"text","text":...}`).
- Assistant output is a list of content blocks (text and/or tool_use), retained in order.

## 7. Structured-output strategy

STR-001 uses Anthropic's **direct Messages API JSON structured output** via
`output_config.format` — `output_config={"format": {"type": "json_schema", "schema": <raw
fixture schema>}}` — which shapes the model's RESPONSE. The raw fixture JSON Schema is preserved
verbatim (no synthetic extraction tool, no helper that could silently transform it), and the
`output_config` actually sent is observable in the raw request artifact. The response is a
native text block; the probe parses it, so raw text and parsed JSON stay separately auditable.

This is complementary to, and NOT interchangeable with, strict tool use: `output_config.format`
constrains the response, whereas `strict: true` on a tool constrains schema-validated tool
INPUT (see TOOL-001). A forced tool call is NOT used to implement STR-001. The Python SDK's
`messages.parse(output_format=...)` is recorded as an SDK convenience path but is not the
primary audit path, because `messages.create(output_config=...)` keeps the raw request
transformation fully observable.

Structured outcomes are classified distinctly so a refusal or a `max_tokens` truncation is never
confused with a schema failure: `schema_validation_passed`, `schema_validation_failed`,
`parse_failed`, `provider_refusal`, `max_tokens_truncation`. (Validation in the probe is a
dependency-free structural check — required keys present — with full JSON Schema validation left
as a harness concern; the raw text and parsed value are always preserved regardless.) Native
JSON structured output is NOT inferred from valid JSON text alone: the request evidence must
confirm `output_config.format`.

## 8. Tool-use representation

TOOL-001 uses Anthropic tool use with `strict: true` (schema-constrained tool INPUT) — a
mechanism separate from and complementary to structured output. `tool_use` blocks preserve id,
name, raw input object, the `strict` flag, and original block order. They are NOT converted into
an OpenAI `function_call` item in raw evidence; the shared audit `tool_call_completed` event is
produced only later by the normalizer. Multiple tool_use blocks would be retained in order;
multiple blocks are never claimed to be parallel execution.

## 9. Streaming lifecycle

The full native lifecycle is preserved in order and NOT collapsed into a single text stream:
`message_start` → `content_block_start` → `content_block_delta` (native `text_delta` or
`input_json_delta` subtypes kept distinct) → `content_block_stop` → (`ping`) → `message_delta`
(carries stop_reason and output usage) → `message_stop`. A `ping` is a genuine but
vocabulary-less native event and is retained.

## 10. Usage and cache metadata

Usage is preserved exactly as exposed. Anthropic splits it across events: input tokens on
`message_start`, output tokens on `message_delta`; the normalizer merges these for the usage
event without fabricating fields. Cache tokens (`cache_creation_input_tokens`,
`cache_read_input_tokens`) are kept under their native keys so cache usage stays distinguishable
from ordinary input usage. Missing usage stays absent (never 0); cache fields absent stay null.
Note: the shared result-record `usage` block maps input/output/total generically; Anthropic's
cache keys differ from OpenAI's, so cache detail lives in the normalized `usage_updated` event
data and the raw evidence rather than in the shared result summary.

## 11. Normalizer behavior

A dedicated Anthropic normalizer maps native evidence into the shared vocabulary: text →
`text_delta`, tool_use → `tool_call_started`/`tool_call_completed`, strict-tool-use structured →
`structured_output_completed` (strategy recorded), usage → `usage_updated`, stop_reason →
`response_completed`. Native behavior with no shared equivalent — content-block lifecycle
(`content_block_start`/`stop`), `ping`, and refusal `stop_reason` — is retained as
`provider_extension`. Because these are provider-native behaviors, they are **never** labelled
`framework_extension` (that label is reserved for framework transformations such as LangChain's).

## 12. Offline comparison status

`alms_audit.reporting.compare.compare_runs` produces a three-lane implementation-shape
comparison (openai-native / langchain / anthropic-native), tagged:

> This is implementation-shape evidence only. It is not live provider semantic evidence.

Structural differences worth live validation (not F1s on their own): for structured output,
BOTH native lanes expose provider-native JSON-schema output (OpenAI Responses API `json_schema`;
Anthropic Messages API `output_config.format`), while the LangChain offline lane selected a
framework-mediated `function_calling` strategy — so the mechanisms are NOT all different; the
meaningful split is native-JSON-schema (openai + anthropic) versus framework-function-calling
(langchain). Additionally, Anthropic exposes an explicit content-block streaming lifecycle the
OpenAI Responses stream does not, and splits usage across stream events while reporting cache
tokens natively.

## 14. Credential status

No credential is needed for P0.6A (offline only). The fail-closed live gate requires a direct
`ANTHROPIC_API_KEY`; an `OPENROUTER_API_KEY` does NOT satisfy it (regression-tested), and no
`base_url` is ever configured. Credential state is presence-only; values are never read or
logged.
