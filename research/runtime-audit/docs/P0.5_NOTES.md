# P0.5 LangChain Control Lane (offline wiring notes)

Research/audit infrastructure only. **No live provider request was made during P0.5.** This
slice adds an isolated LangChain probe lane (`langchain-openai`) that runs the same control
provider/model as the `openai-native` lane so the audit can observe what the framework layer
does at the boundary (DevSpec Section 48). Everything here is offline evidence produced by an
injected fake; live provider semantics remain `unverified_until_live`.

## 1. Selected LangChain versions (checked 2026-07-13)

- `langchain-openai==1.3.5` (released 2026-07-10)
- `langchain-core==1.4.9` (pinned transitively in `probes/langchain/uv.lock`)
- `openai==2.45.0` (transitive) — identical to the `openai-native` probe's direct SDK, so the
  only deliberate difference between the two lanes is the framework layer.

Python `>=3.13`. Versions were resolved by `uv` against PyPI and confirmed by introspecting the
installed packages, not copied from older reports (LangChain moved from the 0.3.x line to 1.x).

## 2. Selected LangChain APIs

- `langchain_openai.ChatOpenAI` — the live model (built with `max_retries=0`, no `base_url`).
- `langchain_core.messages` — `SystemMessage` / `HumanMessage` / `AIMessage` / `AIMessageChunk`.
- `ChatOpenAI.invoke` / `.stream` — generation and streaming.
- `.bind_tools(...)` — tool binding; observed `AIMessage.tool_calls` / `invalid_tool_calls`.
- `.with_structured_output(schema, include_raw=True)` — structured output; the `{raw, parsed,
  parsing_error}` envelope is preserved so the raw message and the parse are both auditable.
- `AIMessage.usage_metadata` / `.response_metadata` — usage and finish metadata.

## 3. Retry ownership (each owner recorded independently)

All automatic retries are disabled and proven, never assumed zero because a fixture requested
zero:

- LangChain runnable retry: none (no `.with_retry()` is applied).
- `ChatOpenAI.max_retries`: 0.
- Underlying `openai` client `max_retries`: 0 (verified: setting `ChatOpenAI(max_retries=0)`
  propagates to `root_client.max_retries == 0`).
- HTTP transport retry: owned by the openai client (governed by the 0 above).

The offline fake counts its own invocations; the probe records `retry_count_observed` from that
measured call count (0 across all six fixtures), not from the request. A regression test asserts
the effective configuration.

## 4. Probe isolation

LangChain lives only in `probes/langchain`. It is absent from `alms/pyproject.toml`, the
harness, and the `openai-native` probe, and the harness process cannot import `langchain_core`,
`langchain_openai`, or `openai` (verified by `find_spec`). The `openai-native` probe and its
lockfile are unchanged. LangChain objects never cross the process boundary — only serialized
JSON does. The harness selects the probe project and normalizer from the lane's `runtime_layer`
(`langchain -> probes/langchain`, `openai -> probes/openai-native`).

## 5. Implemented fixtures

The P0.5 control set only: GEN-001, ROLE-001, STR-001, TOOL-001, STREAM-001, USAGE-001. No
stress, parallel-tool, cancellation, retry, embedding, or multimodal fixtures.

## 6. Offline fake strategy and its limits

The offline model is a narrow custom `BaseChatModel` that `execute()` drives through the REAL
LangChain runnable composition (`bind_tools`, `with_structured_output`, `invoke`, `stream`),
so the framework's message conversion, tool binding, structured-output parser, streaming
aggregation, and usage propagation all run without the network. The live path swaps in the real
`ChatOpenAI`; `execute()` is model-agnostic.

Limit recorded explicitly: the fake does NOT reproduce `ChatOpenAI`'s provider-request/response
translation (how it maps `bind_tools`/`with_structured_output` onto OpenAI request params and
parses the raw provider payload). That translation is `unverified_until_live`.

## 7. Raw framework evidence and its gaps

For each operation the probe preserves the most native evidence LangChain exposes: the
serialized `AIMessage` (content, `tool_calls`, `invalid_tool_calls`, `usage_metadata`,
`response_metadata`, id), stream `AIMessageChunk`s in order plus the framework-aggregated final
message, the structured `{strategy, parsed, parsing_error}` envelope, and framework exception
type with the underlying cause chain. Evidence LangChain does not expose offline is recorded as
absent rather than fabricated: provider request IDs and raw provider usage are
`not_observed_offline` / `unverified_until_live`.

## 8. Framework-boundary observations (offline, implementation-shape only)

These are shape observations from the offline fake, not live findings:

- **Structured output requires a schema title.** LangChain's schema→function conversion raises
  unless the JSON schema has a top-level `title` (used as the function name). The audit injects
  the fixture id as the title and records that it did (`structured_schema_title_injected`). The
  `openai-native` lane instead passes an explicit `name` alongside the schema.
- **Structured output ran as tool-calling.** For the injected model, `with_structured_output`
  used the `function_calling` strategy, so the structured result surfaced as an `AIMessage`
  `tool_call` (normalized: `structured_output_completed` + `tool_call_*`). The `openai-native`
  lane used native `json_schema` and surfaced `output_text`. Whether a live `ChatOpenAI` would
  select `json_schema` is `unverified_until_live`.
- **Streaming synthesized an extra terminal chunk.** LangChain's `.stream()` emitted one more
  chunk than the fake yielded; the extra (empty-content) chunk is preserved as a
  `framework_extension`, so STREAM-001 terminates `PASS_WITH_EXTENSION` in this lane.
- **usage_metadata is the framework's normalized shape**, recorded distinctly from the
  provider's raw usage block; the two are not assumed byte-identical.

## 9. Normalization boundary

A dedicated harness normalizer maps the LangChain envelope into the shared normalized-transcript
vocabulary. Framework-specific behavior that does not fit the vocabulary is emitted as
`framework_extension` (a new, generic event type added to the transcript schema) — never
`provider_extension` (a framework transformation is not provider-native) and never discarded.
No concrete LangChain type name is emitted as an audit event type; framework type detail stays
inside event `data`. `provider_extension` and `framework_extension` are counted separately.

## 10. Offline comparison with openai-native

`alms_audit.reporting.compare.compare_lanes` consumes two offline run directories and reports
per-fixture differences across raw artifact categories, available metadata, event
representation, tool-call representation, structured-output strategy, usage representation,
normalizer extensions, and error representation. Every report carries the disclaimer:

> This is implementation-shape evidence only. It is not live provider semantic evidence.

No F1 is derived from fake-shape differences alone. The differences worth noting (schema-title
requirement, structured-as-tool-calling, synthesized stream chunk) are caused by verified
framework API behavior; they are candidate live checks, not confirmed contract findings.

## 11. Live guardrails (fail-closed, not exercised)

The future live path requires `--live`, `--confirm-live`, a valid budget, a call cap, an
explicit model, a pricing snapshot, the selected lane and fixture subset, the probe env, and a
direct `OPENAI_API_KEY`. It was not executed. `OPENROUTER_API_KEY` does NOT satisfy the
credential gate (a regression test proves an OpenRouter key still yields `BLOCKED_CREDENTIAL`),
and no `base_url` is ever configured — the lane cannot be silently redirected to a gateway.

## 12. Remaining live-only unknowns

`unverified_until_live`: whether a live `ChatOpenAI` selects native `json_schema` vs tool
calling for structured output; real provider event names surviving the framework boundary; real
provider-reported usage vs framework `usage_metadata`; any hidden retry under real network
conditions; real refusal representation; and real model capability behavior. Offline evidence
exercises the pipeline and the shapes the fake models, not the provider's actual behavior.
