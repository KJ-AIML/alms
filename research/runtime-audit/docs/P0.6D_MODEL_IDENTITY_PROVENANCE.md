# P0.6D Model Identity Provenance (finding N-05 closure, offline)

AUDIT INFRASTRUCTURE ONLY. This slice closes the accepted finding N-05 offline. It adds a
neutral, additive, backward-compatible model-identity contract to the shared audit result and
wires all four implemented lanes (openai-native, langchain, anthropic-native, gemini-native) to
it. No live provider request was made during P0.6D.

## 1. N-05 background

The shared audit system recorded the model as a single manifest field, `probe-response.model`,
which holds the requested/configured model id (DevSpec Section 29, "configured model id"). The
served model actually returned by a provider was preserved only inside the raw response artifact,
with no first-class, queryable returned-model field and no provenance. P0.6C accepted N-05 as an
F3 (IMPLEMENTATION_NOTE) with an explicit deferred, non-blocking follow-up that must distinguish
four facts rather than "let every lane populate a bare provider-returned model string". P0.6D
implements that follow-up, offline.

## 2. Previous contract limitation

Before P0.6D, a consumer could not answer, without opening provider-specific raw payloads:

- what model was actually observed in the response evidence;
- whether that observation was a provider-native field, a framework-mediated field, or a
  synthetic offline value;
- which raw artifact justified it;
- whether the observed model matched the requested model.

There was a latent risk that a future change would conflate the requested model with the observed
model, or would label a framework-exposed model id as provider-native merely because the string
resembled a provider model id.

## 3. Requested versus observed semantics

- `requested_model` is request-side configuration evidence: the explicit id placed into the probe
  request. It is never overwritten by response metadata.
- `observed_returned_model` is a model id actually observed in response-side evidence. It is
  optional. When the selected API/lane exposes no returned model id, it is recorded as unavailable
  rather than copied from the requested model.

The system never assumes the model requested is the model observed, and never assumes a model
identifier exposed through a framework is directly provider-native.

## 4. Provenance vocabulary

`observed_returned_model_source` draws from the centrally-owned provenance vocabulary
(`harness/src/alms_audit/provenance.py`); no probe-specific vocabulary is introduced. The subset
that may legitimately label an observed returned model is `MODEL_IDENTITY_SOURCES`:

- `provider_native` — a model id read from a native provider response (live).
- `framework_native` — a model id exposed only through framework response metadata (live). Never
  provider-native even when the string resembles a provider id.
- `sdk_convenience` — a model taken from an SDK convenience projection rather than the
  authoritative resource. The normalizers deliberately do not use this as authority.
- `fixture_expected` — an offline synthetic (mock/fixture) value. Corresponds to
  `execution_mode == "offline_mock"`. Never labelled provider/framework-native.
- `unavailable` — no returned model was reported; the value is not knowable here.
- `unverified_until_live` — a claim only a real provider call can settle.

The requested model is request-side configuration, not an observation, so it never carries one of
these.

## 5. Lane-by-lane extraction

Each normalizer extracts the observed returned model from its OWN native shape via
`extract_model_identity(capture_kind, raw_obj)` and exposes `MODEL_IDENTITY_LIVE_SOURCE`. The
shared result builder holds no provider-specific path; it only delegates.

- OpenAI native: served model read from the authoritative Responses object (`response.model` for a
  non-stream capture; the `response.completed` stream event's `response.model`). Live source
  `provider_native`. No alias/snapshot resolution.
- Anthropic native: served model read from the native Message resource (`message.model`;
  `message_start.message.model` for a stream). Live source `provider_native`. A missing Message
  model stays unavailable, never substituted from the requested model.
- Gemini native: served model read from the FULL Interaction resource (`interaction.model`;
  `reconstructed.model` or `interaction.completed.interaction.model` for a stream), NOT the
  `output_text` SDK convenience projection. Live source `provider_native`.
- LangChain: model id exposed through framework `response_metadata.model_name` (or `model`) on the
  AIMessage / final aggregated chunk. Live source `framework_native` — never `provider_native`,
  regardless of how the string looks. If the framework exposed no model metadata, the value is
  unavailable and the requested model is never copied in.

## 6. Offline versus live distinction

Execution mode and source provenance are related but distinct axes, and both are preserved. In
`offline_mock` mode every observed value is `fixture_expected` — an offline provider-shaped object
is not a real provider observation. Only under a `live` run does a lane's `MODEL_IDENTITY_LIVE_SOURCE`
(`provider_native` for the native lanes, `framework_native` for LangChain) apply. The result record
carries `execution_mode` alongside `observed_returned_model_source` so the two are never conflated.

## 7. Compatibility strategy

The change is additive. The legacy optional `probe-response.provider_returned_model` field is
retained (its comment updated) so older probe-response artifacts still validate; it asserts no
provenance and is not the authoritative surface, and the probes still do not populate it. The
authoritative cross-lane contract lives on the RESULT record as `observed_model_identity`, derived
by the harness normalizer from the raw response artifact — which already preserves the returned
model as plain JSON (never an SDK object crossing the subprocess boundary). No field was deleted or
renamed; no older Phase 0 evidence became invalid. There are no duplicate authoritative model
fields: the manifest holds the requested model, and the result holds the neutral identity summary.
If a future artifact carries both the legacy `provider_returned_model` and the new result field,
the result-level `observed_model_identity` is the authority.

## 8. Mismatch semantics

A mismatch between `requested_model` and `observed_returned_model` is observable via
`model_identity_match` (`true` / `false` / `unknown`), an EXACT-STRING comparison that requires no
canonicalization. A mismatch does NOT automatically mean failure: possible causes include provider
alias resolution, snapshot routing, framework metadata transformation, gateway behavior, or (here)
synthetic offline fixture behavior. P0.6D records the mismatch; it does not interpret it as safe,
unsafe, expected, or erroneous without evidence. The audit `status` verdict is unaffected — a
mismatch never produces `ERROR_RUNTIME` or `FAIL_INVARIANT`. A concrete offline example: the
LangChain mock exposes `response_metadata.model_name == "offline-fake"`, which differs from the
requested model, so its offline result shows `model_identity_match == "false"` while remaining a
valid PASS/PASS_WITH_EXTENSION result.

## 9. Schema changes

- `spec/result.schema.json` (additive, optional): `observed_model_identity` with
  `requested_model`, `observed_returned_model`, `observed_returned_model_source` (central 9-term
  enum), `observed_returned_model_raw_ref`, `execution_mode`, and `model_identity_match`. An
  if/then clause enforces the invariant that a populated `observed_returned_model` (a string) must
  carry a non-empty `observed_returned_model_raw_ref`. `additionalProperties: false` discipline is
  unchanged elsewhere (result top-level was already open; the matrix and transcript event closures
  are untouched).
- `spec/probe-response.schema.json`: `provider_returned_model` comment updated to record N-05 as
  resolved_offline and to name the authoritative result-level surface. The field remains optional
  legacy.
- `harness/src/alms_audit/provenance.py`: `MODEL_IDENTITY_SOURCES` frozenset added (subset of the
  owned 9-term vocabulary) so the model-identity source enum is centrally owned.

## 10. Comparison changes

`reporting/compare.py` now surfaces, per lane per fixture, a `model_identity` view: requested
model, observed returned model, observed model source, raw-reference presence,
requested/observed exact-string equality, availability state, and execution mode. Every offline
comparison carries a `model_identity_note` stating that observed returned model values are
synthetic offline evidence unless explicitly marked live, and that no provider routing behavior is
inferred from offline fake values. The machine-readable neutrality matrix
(`reports/protocol-neutrality-matrix.json`) gains a `model_identity` dimension recording, per lane:
request model location, returned model location, returned model authority, provenance
classification, raw evidence location, offline availability, and known limitations. N-05 is marked
`resolved_offline`. The matrix validates against `spec/protocol-neutrality-matrix.schema.json`.

## 11. Remaining live-only unknowns

The following stay `unverified_until_live` and are NOT claimed verified by P0.6D:

- That a real provider returns a served model that differs from the requested id (dated snapshot,
  alias resolution, gateway routing).
- That the live source for each native lane is genuinely provider-native as read from a real
  response, and that LangChain's live `response_metadata.model_name` reflects the framework's
  actual behavior.
- Any interpretation of a requested/observed mismatch as safe, expected, or erroneous.

## 12. N-05 resolution status

N-05 is classified `resolved_offline`: the cross-lane contract is implemented, provenance is
explicit, no fallback fabrication exists, all four lanes are wired, and the compatibility and
negative tests pass. Actual live returned-model behavior (provider routing, alias/snapshot
resolution) remains `unverified_until_live`. No provider routing or alias behavior has been
verified. No live provider request was made during P0.6D.
