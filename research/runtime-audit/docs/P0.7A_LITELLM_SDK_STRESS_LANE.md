# P0.7A — LiteLLM SDK Abstraction Stress Lane

Audit infrastructure only. Offline implementation and verification. This document records what
LiteLLM's Python **SDK** abstraction layer preserves, converts, synthesizes, drops, renames,
estimates, and canonicalizes, measured against the provider-neutral contract established in P0.6C
(protocol neutrality) and P0.6D (model identity, finding N-05).

**No live provider request was made during P0.7A. The LiteLLM Proxy Server was not started.**

The objective is not to prove LiteLLM good or bad. It is to measure abstraction loss and false
equivalence. Everything below is implementation-shape evidence only; it is not live provider
semantic evidence.

## 1. Selected LiteLLM version

- Package: `litellm==1.92.0` (pinned; dedicated lockfile `probes/litellm-sdk/uv.lock`).
- Python requirement: `>=3.13`.
- Date checked: 2026-07-13, by importing and exercising the installed SDK offline (not from
  memory or older-release examples).
- Response type: `litellm.types.utils.ModelResponse` (OpenAI ChatCompletion-shaped).
- Stream type: `litellm.litellm_core_utils.streaming_handler.CustomStreamWrapper` yielding
  `ModelResponseStream` chunks (`object="chat.completion.chunk"`).
- Retry ownership: `litellm.num_retries` (default `None`; forced `0`); per-call `num_retries=0`.
- Fallback ownership: none — no `Router` is constructed, so no fallbacks / load balancing.
- Callback state: `success_callback`/`failure_callback`/`input_callback`/`callbacks` all `[]`.
- Cache state: `litellm.cache = None`.
- Telemetry state: `litellm.telemetry` default `True` -> forced `False`.
- Known provider-normalization behavior: presents unlike providers through an OpenAI-Chat-
  Completions-shaped abstraction; strips the provider prefix on the returned model field;
  synthesizes usage via `token_counter` on the mock path.
- Known unavailable provider-native evidence: real provider request shape/headers/routing/alias
  resolution/cost/retry/exception-from-network — all `unverified_until_live`.

## 2. SDK rather than Proxy boundary

This lane audits the LiteLLM Python SDK (`litellm.completion`). It does not audit the LiteLLM
Proxy Server, virtual keys, gateway authentication, proxy rate limiting, proxy database state,
proxy administration APIs, router, fallbacks, load balancing, multiple deployments, caching,
telemetry callbacks, observability integrations, or spend tracking. The lane id is `litellm-sdk`
(never `litellm-proxy`, `openai-native`, `openai-compatible-provider`, or `openrouter`). The
reserved `litellm` (gateway) config entry is left untouched for a future server-boundary slice.

Boundary evidence: `fastapi` (a proxy-server dependency) is deliberately absent from the probe
env (`test_subprocess.py::test_fastapi_absent_confirms_sdk_not_proxy`). Notably, passing `tools`
directly to `litellm.completion` in 1.92.0 routes through LiteLLM's proxy MCP utilities, which
import `fastapi` — an SDK/proxy entanglement documented in section 10.

## 3. API surface

The direct synchronous SDK completion surface: `litellm.completion(...)`. This lane audits
LiteLLM's Chat-Completions-shaped abstraction and not every LiteLLM API surface (a Responses-style
API would be a separate fixture or future lane). Both API families are not mixed here. An explicit
provider-qualified synthetic model string (`openai/gpt-synthetic-p07a`) is used offline; there is
no hidden default model.

## 4. Routing semantics

`litellm.get_llm_provider(model)` is observed per run and preserved separately from the returned
model. A provider-qualified string routes by its prefix: `openai/gpt-x -> ('gpt-x', 'openai', ...)`.
A bare (unqualified) model string raises `BadRequestError` and is recorded as a routing error
rather than silently defaulted to a provider (`test_retry_safety.py::test_unqualified_model_has_
no_hidden_default`). The provider prefix is preserved in the request evidence and never stripped
from the request. The actual provider request/route stays `unverified_until_live`; routing is not
inferred from the string alone beyond what `get_llm_provider` reports.

## 5. Request transformation

`litellm.utils.get_optional_params` translates SDK arguments into provider params. For structured
output the `response_format` json_schema is translated (request-side transformation exercised
offline). For tools, `get_optional_params(tools=...)` is exercised and its output recorded, while
`tools` is deliberately NOT forwarded to `litellm.completion` (which routes through the proxy MCP
path). The submitted `litellm_request.json` records exactly what was asked of the SDK.

## 6. Response normalization

LiteLLM returns a `ModelResponse` (`id`, `created`, `model`, `object`, `system_fingerprint`,
`choices[].message`, `usage`) plus `_hidden_params` (auxiliary metadata: `api_base`,
`litellm_model_name`, `response_cost`, `litellm_call_id`, `_response_ms`, ...). The probe preserves
the full `model_dump()` and `_hidden_params` verbatim. The harness `litellm` normalizer reads only
this plain JSON (never a litellm object) and treats the OpenAI-shaped container as framework-owned:
`_hidden_params`, routing, and tool-request-translation become `framework_extension` events, never
`provider_extension`. LiteLLM's OpenAI-compatible output is not treated as OpenAI provider evidence.

## 7. Retry and fallback ownership

Every retry/repeat owner is disabled and proven from effective state, never assumed zero because a
fixture requested zero: `litellm.num_retries = 0` (module) and `num_retries=0` (per call); no
`Router` (so no fallbacks, context-window fallbacks, content-policy fallbacks, or load balancing);
the harness/probe make exactly one call per fixture. Tests prove exactly one call and zero retries,
and that a structured parse does not trigger a second call
(`test_retry_safety.py`). No live transport retry behavior is claimed offline.

## 8. Callbacks, telemetry, and cache

`configure_litellm_isolation()` forces `telemetry=False`, `suppress_debug_info=True`, empty
`success_callback`/`failure_callback`/`input_callback`/`callbacks`, and `cache=None`; the effective
state is recorded in every run's `isolation` block as evidence. A network tripwire
(`ALMS_PROBE_BLOCK_NETWORK=1`) fails the run on any outbound socket; importing litellm makes no
network call because the probe forces `LITELLM_LOCAL_MODEL_COST_MAP=True` on import (without it,
`import litellm` fetches a remote model-cost map from GitHub — a real import-time network attempt
that the tripwire would otherwise catch). No prompt, response, usage, or metadata leaves the
process.

LiteLLM also prints promo/info banners to stdout; the probe redirects all stdout to stderr during
execution so the only thing on real stdout is the one-line manifest the harness parses
(`test_subprocess.py::test_mock_subprocess_stdout_is_clean_single_line_manifest`).

## 9. Structured-output handling

`STR-001` requests `response_format` json_schema; the strategy `response_format.json_schema` is
recorded exactly. The probe performs a local JSON parse and a local schema-presence check, kept
distinct from the raw text, and records `provider_validation = unverified_until_live`. There is no
silent fallback to tool calling. Valid JSON alone is not treated as native structured-output proof.
The comparison classifies the mechanism as `framework_response_format (litellm sdk)`, NOT
`native_json_schema` — it joins LangChain on the framework side.

## 10. Tool-call handling

`TOOL-001` did NOT execute the full `litellm.completion(tools=...)` path. That path in 1.92.0
routes through LiteLLM's proxy MCP utilities, which import `fastapi` (a proxy-server dependency
deliberately absent from this SDK-only probe). Instead the lane exercises a **partial** path
(execution path components `framework_request_transformation` + `framework_response_object_
injection`), classified per fixture in section 10a and recorded as finding L-01 (section 15).

TOOL-001 evidence boundary:

- **Verified offline**: explicit model routing inspection (`get_llm_provider`); tool request
  schema transformation (`get_optional_params`, recorded in `tool_request_translation`); the
  LiteLLM tool-call response representation (a real `ModelResponse` with tool_calls); tool-call id,
  name, raw arguments string, and ordering; normalization and result construction; no tool
  execution; no parallel-execution inference.
- **Not verified offline (`unverified_until_live`)**: the complete `litellm.completion(tools=...)`
  path; provider adapter translation; provider request creation; network exception mapping;
  provider-returned tool semantics.

Tools are not executed; parallel execution is never inferred; framework tool-call ids are not
assumed to be provider ids. FastAPI is NOT added to force the full path — that would blur the
SDK/Proxy boundary this lane establishes.

## 10a. Per-fixture execution path (evidence accuracy)

The six fixtures do NOT all use an identical execution path; a path is recorded as exercised only
when it was actually run, never because an output type was instantiated. The probe classifies each
fixture and records it in the raw envelope (`execution_path`), surfaced in the transcript, the
five-lane comparison (`execution_path_by_lane`), and the matrix
(`fixture_coverage.litellm-sdk.execution_paths`).

Vocabulary: `completion_mock_response` (litellm.completion(mock_response=str) fully exercised);
`framework_request_transformation` (get_optional_params param translation, inside completion for
response_format or as an explicit external step for tools); `framework_response_object_injection`
(a litellm ModelResponse injected as the mock, used for tool_calls a string mock cannot express);
`full_provider_adapter` (the real provider path — never offline); `full_completion_tools_path`
(litellm.completion(tools=...) end to end — NOT exercised).

- **GEN-001** — `completion_mock_response`. Coverage: offline completion mock path.
- **ROLE-001** — `completion_mock_response`. Coverage: offline completion mock path.
- **STR-001** — `completion_mock_response` + `framework_request_transformation` (response_format
  translated inside completion). Coverage: offline completion mock path.
- **TOOL-001** — `framework_request_transformation` + `framework_response_object_injection`.
  Coverage: **partial** (`full_completion_tools_path_exercised = false`).
- **STREAM-001** — `completion_mock_response` (streaming). Coverage: offline completion mock path.
- **USAGE-001** — `completion_mock_response` (usage framework-synthesized by token_counter).
  Coverage: offline completion mock path.

`full_provider_adapter` is never exercised in any fixture; it stays `unverified_until_live`. This
is implementation-shape evidence only; it is not live provider semantic evidence.

## 11. Streaming handling

`STREAM-001` runs `litellm.completion(stream=True, stream_options={"include_usage": True})`,
producing a `CustomStreamWrapper` over `ModelResponseStream` chunks. Chunk order is preserved,
text deltas are captured, an `include_usage` terminal usage chunk is captured distinctly, and the
aggregate is reconstructed via `stream_chunk_builder`. LiteLLM chunks are labelled framework
(`response_started` native_type `litellm_model_response_stream`), never provider events. Live event
delivery is `unverified_until_live`.

## 12. Usage provenance

LiteLLM's `ModelResponse.usage` is OpenAI-shaped (`prompt_tokens`/`completion_tokens`/
`total_tokens` + `prompt_tokens_details`/`completion_tokens_details`) but LiteLLM-owned. It is
labelled `framework_native` (usage `source`), never `provider_native` — the N-01 stress. Cache
reads (`prompt_tokens_details.cached_tokens`) and reasoning (`completion_tokens_details.reasoning_
tokens`) survive into the summary (N-02); missing usage stays null (never 0). Offline the usage is
synthesized by `token_counter`, so the real provider usage block stays `unverified_until_live`.
`response_cost` from `_hidden_params` is a LiteLLM estimate (null for the unpriced synthetic model)
and is never labelled billed cost.

## 13. Error mapping

LiteLLM normalizes failures into its OWN OpenAI-shaped exception taxonomy
(`InternalServerError`/`BadRequestError`/`RateLimitError`/... with `llm_provider`, `status_code`,
`model`, and an underlying cause chain). The probe preserves the LiteLLM exception class, cause
chain, provider name, status, and model; the harness records them without flattening and without
labelling a LiteLLM-generated exception class as provider-native. Exercised offline via LiteLLM's
mock exception seam (`test_retry_safety.py::test_error_scenario_maps_to_litellm_exception_
taxonomy`). No live error fixture is authorized; real network-mapped exceptions stay
`unverified_until_live`.

## 14. Model identity provenance (P0.6D / N-05 applied)

`observed_model_identity` on the result record distinguishes `requested_model` (e.g.
`openai/gpt-synthetic-p07a`) from `observed_returned_model` (the `ModelResponse.model` LiteLLM
returns). LiteLLM STRIPS the provider prefix: observed `gpt-synthetic-p07a` != requested
`openai/gpt-synthetic-p07a`, a genuine offline mismatch recorded as `model_identity_match=false` —
never corrected (no lowercasing / alias resolution / snapshot stripping / family inference) and
never turned into an error. `observed_returned_model_source` is `fixture_expected` offline and
`framework_native` live (never `provider_native`, even though the string is OpenAI-shaped). The
full requested string survives on the framework side only, in `_hidden_params.litellm_model_name`.
A missing returned model stays `unavailable`, never copied from the requested model.

## 15. Protocol-neutrality findings

The lane was specifically stress-tested against the resolved defects and does NOT reintroduce them:

- **N-01** (framework usage must not become provider-reported): LiteLLM's OpenAI-shaped usage is
  labelled `framework_native`, not `provider_native`. Held.
- **N-02** (non-OpenAI usage details must not be dropped by OpenAI-shaped paths): cache-read and
  reasoning tokens survive into the summary; missing stays null. Held.
- **N-03** (native/abstraction terminal state must remain observable): `finish_reason` surfaces
  as `observed_terminal_state` with `source=framework_native`. Held.
- **N-04** (derived fields use central provenance): usage and model-identity sources come from the
  centrally-owned `provenance` vocabulary. Held.
- **N-05** (requested and returned model identity must remain separate): requested vs observed are
  distinct fields; the prefix-strip mismatch is recorded, not conflated. Held.

One proposed implementation finding is recorded:

- **L-01 (proposed, F2, tool_semantics)** — LiteLLM SDK tool path couples to MCP/proxy-oriented
  dependencies. Invoking the selected completion surface with tool configuration
  (`litellm.completion(tools=...)`) in the proxy-free isolated environment imports LiteLLM
  utilities that require FastAPI. Impact: the SDK-only lane cannot exercise the complete TOOL-001
  completion path without introducing server-layer dependencies; request transformation
  (`get_optional_params`) and response representation (LiteLLM ModelResponse tool-call types)
  remain testable separately and are what the lane exercises. Contract impact: no shared ALMS
  evidence contract failure was observed (no false provenance, no false semantic equivalence, no
  contract loss). Live status: the full path, provider adapter translation, provider request
  creation, network exception mapping, and provider-returned tool semantics remain
  `unverified_until_live`. Not classified F1 — no reproducible shared-contract loss or false
  provenance was found.

No new F1 is created. Shape differences alone are not findings; an F1 requires reproducible
contract loss, false provenance, or false semantic equivalence, none of which the correctly-handled
lane exhibits. The prefix-strip, framework-native usage, structured framework-mediation, and
SDK/proxy `fastapi` entanglement (L-01) are documented observations, not defects in the audit
contract.

## 16. Offline limitations

- All evidence is offline via LiteLLM's `mock_response` seam. It exercises routing, request
  translation, `ModelResponse` typing, `_hidden_params`, and the streaming wrapper, but NOT the
  provider request/response translation.
- Offline usage is synthesized (`token_counter`), not provider-reported.
- The tool-call response shape is injected via LiteLLM types; provider -> LiteLLM tool translation
  is not exercised offline.
- Structured output returns injected JSON; provider validation is not exercised offline.
- Errors are exercised via the mock exception seam, not a real network response.
- LiteLLM spawns a background async logging task; on Windows this produces harmless GC-time
  asyncio cleanup warnings after the manifest is already written (no effect on exit code or the
  manifest).

## 17. Remaining live-only checks (`unverified_until_live`)

Real provider request shape and headers; actual provider routing and alias/snapshot resolution;
whether the returned model prefix-strip matches live provider behavior; real cost calculation and
billed cost; real retry/fallback behavior; the tool-call request path when routed through the
provider (and whether the fastapi/MCP entanglement affects live tool use); native structured-output
strictness vs prompting fallback; and real exception mapping from a network response. Each remains
`unverified_until_live` and requires a gated live run, out of P0.7A scope. P0.7B is not begun.
