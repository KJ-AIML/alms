# P0.6B Gemini Native Interactions Lane (offline wiring notes)

Research/audit infrastructure only. **No live provider request was made during P0.6B.** This
slice adds an isolated Gemini native probe lane (`gemini-native`) using the google-genai
**Interactions API** (`client.interactions.create`) that preserves Interactions-native concepts
(Interaction resource, chronological steps, response_format, native stream events) rather than
reshaping to OpenAI items (DevSpec Section 51). Everything here is offline evidence produced by
an injected fake returning native Interaction dictionaries; real Gemini behavior remains
`unverified_until_live`.

## 1. google-genai version and API status

- `google-genai==2.11.0` (resolved and pinned 2026-07-13), pinned in
  `probes/gemini-native/uv.lock`. Python `>=3.13`. No `openai`/`anthropic`/`langchain` pulled.
- **Gemini Interactions API: Generally Available since June 2026 and recommended by Google for
  new projects.**
- **google-genai 2.11.0 public Python surface: exposed through `google.genai.interactions`.**
- **SDK implementation detail: the public module re-exports generated types and resources
  implemented under internal `_gaos` modules.** This is an implementation detail, not the API
  lifecycle.
- **Stability note: generated Python types, signatures, and agent-specific helpers may evolve
  even though the underlying Interactions API is GA.** Implementation risk kept: `client.
  interactions.create` and its generated request types must be revalidated when google-genai is
  upgraded.
- The "Agents usage is experimental" warning is agent-specific — verified in the installed
  source to fire only from the `client.agents` property (`_agent_experimental_warned`); it does
  NOT apply to model Interaction requests, and this probe never accesses `client.agents`.
- Verified by resolving the SDK and introspecting the installed signatures/types — not from
  obsolete `google-generativeai` examples.

## 2. Selected Interactions API surface

`google.genai.Client(...).interactions.create(request=<CreateModelInteraction>)` — direct
Gemini (not Vertex). `models.generate_content` is deliberately NOT the audit surface (recorded
as an alternative). No OpenAI-compatibility endpoint, no Vertex mode, no custom `base_url`.
Confirmed request/response types: `CreateModelInteraction` (`model`, `input`, `stream`, `store`,
`system_instruction`, `tools`, `response_format`, `previous_interaction_id`, ...); `Interaction`
(`id`, `status`, `model`, `created`, `steps`, `usage`, `output_text`); step union
(`UserInputStep` / `ModelOutputStep` / `FunctionCallStep{arguments,id,name,type}` /
`ThoughtStep`); `TextResponseFormat{mime_type, jsonSchema}` via `ResponseFormat.text`; status
literals (`in_progress`/`requires_action`/`completed`/`failed`/`cancelled`/`incomplete`/
`budget_exceeded`); native stream events (`interaction.created`/`step.start`/`step.delta`/
`step.stop`/`interaction.completed`) with `text_delta`/`arguments_delta`/`thought_signature_delta`
subtypes.

Because the SDK's generated Interactions types are re-exported from internal `_gaos` modules and
may evolve on upgrade (the API itself is GA), offline evidence uses schema-validated native
dictionaries with the SDK's real field names; the exact typed wire objects are
`unverified_until_live`, and `client.interactions.create` must be revalidated on SDK upgrade.

## 3. store=false policy

`store=false` is set on EVERY request (verified across all six fixtures in both the probe and
the harness offline simulation). `previous_interaction_id` is never set; each base fixture is
stateless single-turn. No server-side state is created, reused, or tested in P0.6B. Regression
tests assert store=false on every request, no `previous_interaction_id`, no hidden
storage-enabling default, and no server-state identifier reuse.

## 4. SDK retry and timeout ownership

The live client is built with `HttpOptions(timeout=<ms>, retry_options=HttpRetryOptions(
attempts=1))` — **configured for one total attempt and therefore zero configured retries** — and
`vertexai` off (direct `generativelanguage.googleapis.com`, no redirect). Timeout is owned by
`HttpOptions.timeout`. Probe/harness/subprocess retries: none configured. **Effective live
transport behavior: `unverified_until_live`** — real network retry behavior has NOT been
empirically verified (no live call was made). Reported separately: the offline injected fake was
observed to be called exactly once per fixture (0 retries measured) across all six fixtures, and
no retry occurs after invalid structured output or a provider error in the offline path.

## 5. Fixture coverage

The P0.6 base control set only: GEN-001, ROLE-001, STR-001, TOOL-001, STREAM-001, USAGE-001. No
stress, parallel-tool, cancellation, retry, embedding, or multimodal fixtures (multimodal is out
of this slice even though Gemini supports it).

## 6. Interaction resource shape and step/content-part semantics

The authoritative response is the full Interaction resource (`id`, `object`, `status`, `model`,
`created`, `steps`, `usage`) — NOT reshaped into OpenAI items. `output_text` is captured
separately as an SDK convenience projection, never as the only artifact. The system instruction
is a TOP-LEVEL `system_instruction` (never a user-input message). Input is a list of
chronological steps (a `user_input` step with ordered content parts). Model output is a
`model_output` step with ordered text content parts. The requested model (manifest) and the
provider-returned model (on the Interaction) are kept separate.

## 7. Thought-signature safety

Thought steps and `thought_signature_delta` events are preserved ONLY as opaque structural /
protocol evidence: the normalizer records thought-step presence and signature PRESENCE (a
boolean), never the signature value in normalized events and never any reasoning text. No hidden
chain-of-thought is requested; thought data is not normalized into assistant reasoning text, is
not claimed equivalent to model output, and is never printed in reports. `total_thought_tokens`
is retained as usage evidence. P0.6B does not implement multi-turn continuation.

## 8. Structured output (response_format)

STR-001 uses the native Interactions `response_format`:
`{"text": {"mime_type": "application/json", "jsonSchema": <raw fixture schema>}}`. The raw fixture
JSON Schema is preserved verbatim under the SDK's `jsonSchema` field and the `response_format`
actually sent is observable in the raw request artifact. It is NOT implemented through a synthetic
function tool (STR-001 sends no tool). The response is a native `model_output` text block which
the probe parses; raw text and parsed JSON are kept distinct. Outcomes are classified distinctly:
`schema_validation_passed`, `schema_validation_failed`, `parse_failed`, and `interaction_incomplete`
(a non-`completed` status) — so an incomplete interaction is never confused with a schema failure.
Native structured output is not inferred from valid JSON alone: the request evidence must confirm
`response_format`.

## 9. Function-call steps

TOOL-001 uses a native Interactions function tool. The `function_call` step preserves its id,
name, arguments object, and original step order; the Interaction status is `requires_action`.
Only the first function-call step is captured; no function result is submitted (no second
provider turn). The step is never converted into an OpenAI function item in raw evidence;
multiple function-call steps would not be claimed as parallel execution.

## 10. Streaming lifecycle

The full native lifecycle is preserved in order and NOT collapsed into text chunks:
`interaction.created` -> `step.start` -> `step.delta` (native `text_delta` / `arguments_delta` /
`thought_signature_delta` subtypes kept distinct) -> `step.stop` -> (unknown native event) ->
`interaction.completed` (carries terminal status and usage). Unknown native events are retained
as `provider_extension`; thought-signature deltas are retained structurally.

## 11. Usage representation

Usage is preserved exactly as exposed (`total_input_tokens`, `total_output_tokens`,
`total_tokens`, `total_thought_tokens`, `total_cached_tokens`) in raw evidence and in the
normalized `usage_updated` event. For the shared result summary, the normalizer MAPS the Gemini
totals to the common token names (this is normalization, explicitly permitted, while the native
object is preserved). Missing usage stays absent (never 0); cache and thought tokens stay
distinct from ordinary input/output tokens.

## 12. Gemini normalizer behavior

A dedicated Gemini normalizer maps native evidence to the shared vocabulary: `model_output`
text -> `text_delta`, `function_call` step -> `tool_call_started`/`tool_call_completed`,
`response_format` structured -> `structured_output_completed` (strategy recorded), usage ->
`usage_updated`, status -> `response_completed`. Interactions-native concepts with no shared
equivalent — step lifecycle (`step.start`/`stop`), thought steps/signatures, `requires_action`,
and unknown native events — are retained as `provider_extension`. Because these are
provider-native concepts, they are **never** labelled `framework_extension`.

anthropic-native / gemini-native), tagged:

## 15. Credential status

No credential is needed for P0.6B (offline only). The fail-closed live gate reads ONLY
`GEMINI_API_KEY`. The following do NOT satisfy it (regression-tested): `GOOGLE_API_KEY` (the SDK's
other auto-discovery key), `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`
and Vertex environment variables. No `base_url` / Vertex mode is ever configured.

Auto-discovery isolation: the live client is constructed EXPLICITLY as
`genai.Client(api_key=<GEMINI_API_KEY value>, ...)` — never arg-less `genai.Client()` — so
google-genai's `GEMINI_API_KEY`/`GOOGLE_API_KEY` auto-discovery is never used. Verified in the
installed SDK: with `GOOGLE_API_KEY` set to a different value, the explicitly-constructed client's
`api_key` is the passed Gemini value, not the auto-discovered one. The gate reads only
`GEMINI_API_KEY` and fails closed (BLOCKED_CREDENTIAL) before any client is constructed, so a
present `GOOGLE_API_KEY` cannot create a client. Credential state is presence-only; the key value
is never printed, serialized, hashed, measured, or returned across the process boundary.
