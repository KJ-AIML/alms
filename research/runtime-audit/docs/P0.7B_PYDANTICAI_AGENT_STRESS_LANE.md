# P0.7B — PydanticAI Agent Framework Stress Lane

ALMS Phase 0 Runtime Audit Lab. This slice adds an isolated PydanticAI **Agent** audit lane
(`pydantic-ai-agent`) and measures what the Agent abstraction preserves, transforms, validates,
retries, defers, aggregates, and exposes, against the provider-neutral audit contract established
in P0.6C and P0.6D.

Offline implementation and verification only. **No live provider request was made during P0.7B.
The Pydantic AI Gateway and Logfire were not used. No tool was executed.** Everything below is
implementation-shape evidence, not live provider semantic evidence, and not the ALMS runtime
contract. Real provider behavior remains `unverified_until_live`.

Baseline: published P0.7A commit `08a1730` (five-lane matrix; L-01 recorded F2/proposed; N-01..N-05
resolved_offline). L-01 is treated as-is and not modified by this slice.

## 1. PydanticAI version

Pinned `pydantic-ai-slim==2.9.0` (import name `pydantic_ai`, version 2.9.0), python `>=3.13`,
resolved into a dedicated lockfile in `probes/pydantic-ai-agent/`. The slim distribution is used
deliberately: it brings the Agent, the graph engine (`pydantic-graph`), and the `FunctionModel`
test seam without any vendor provider SDK, so no real provider model can be constructed. Every API
used was verified against the installed source and signatures, not from memory or obsolete
examples.

## 2. Agent boundary

The lane audits the PydanticAI **Agent** (DevSpec Section 53): the Agent graph, the framework
message/part model, structured-output strategies, tool and deferred-tool behavior, framework retry
ownership, stream events, run-level usage aggregation, model identity, framework terminal states,
and framework exceptions.

It does **not** audit the Pydantic AI Gateway, Pydantic Evals, Pydantic Graph as a standalone
product, MCP servers, durable-execution integrations, Logfire, OpenTelemetry export, or
provider-native semantics. No custom provider endpoint is configured and no Router / FallbackModel
is used. The `Agent` API is the primary surface; the low-level `direct` API is not used as the
primary lane because it omits much of the framework-owned behavior under audit.

## 3. FunctionModel seam

The only model used offline is `FunctionModel` (`pydantic_ai.models.function.FunctionModel`),
PydanticAI's own explicit-control test seam. It runs the real Agent graph, message/part model,
output-strategy selection, validation, deferred-tool handling, usage aggregation, and stream
events with zero network. It gives explicit control over `ModelRequest`, `ModelResponse`,
`ModelResponsePart`s, stream events, usage, `model_name`, tool calls, structured output, and
errors. Non-stream fixtures supply a `function`; the stream fixture additionally supplies a
`stream_function`. What FunctionModel does NOT exercise is any real provider request/response
semantics.

## 4. TestModel exclusion rationale

`TestModel` is deliberately NOT the primary evidence generator. It procedurally creates
schema-valid output and auto-calls registered tools, which would hide the framework behavior this
lane measures (whether NativeOutput was actually selected, whether a tool call defers, what the
model response parts contain). Using it as the evidence source would fabricate agreement rather
than observe framework behavior. FunctionModel gives explicit control instead.

## 5. ALLOW_MODEL_REQUESTS policy

`pydantic_ai.models.ALLOW_MODEL_REQUESTS` is set to `False` before any Agent or model execution
(the default is `True`). FunctionModel is exempt from that gate (it is a test model), so the
offline lane still runs while every real provider model is blocked. A process-level network
tripwire is additionally installed: it blocks all outbound sockets and allows only the asyncio
loopback self-pipe (127.0.0.1) that an async Agent run needs on Windows. A real provider request
targets an external host and is hard-blocked; the tripwire keeps its meaning.

## 6. Fixture coverage

Exactly the six base fixtures: `GEN-001`, `ROLE-001`, `STR-001`, `TOOL-001`, `STREAM-001`,
`USAGE-001`. Each fixture maps to one probe subprocess invocation via Probe Process Protocol v0:

```
Harness CLI -> planner -> runner -> isolated PydanticAI probe subprocess -> Agent -> FunctionModel
-> Agent graph and framework messages/events -> raw evidence -> probe response -> PydanticAI
normalizer -> result record -> run summary
```

All six run in `offline_mock` mode with zero provider calls, zero network connections, zero
credentials, and zero tool executions. Evidence:
`harness/tests/test_lane_dispatch.py::test_full_offline_pydanticai_simulation_all_six`.

## 7. Agent instructions and message parts

A fixture `system` message is mapped to the Agent `instructions` channel; PydanticAI renders it as
a framework `InstructionPart`, a framework-owned request part. A `user` message becomes a
`UserPromptPart`. Message order is preserved and the full `ModelRequest` / `ModelResponse` part
sequence is captured via `all_messages_json`. Framework message parts are never labelled
provider-native, and the framework Agent instruction is distinguished from a provider-native system
instruction (ROLE-001 evidence). Where the framework merges or synthesizes request parts, that is
recorded verbatim rather than reshaped.

## 8. NativeOutput strategy

For `STR-001` the output type is `NativeOutput(StructuredDict(schema))`. The observed
`ModelRequestParameters.output_mode` is `native` (recorded in the raw evidence), the generated JSON
Schema is retained, and the parsed output (`{"name": "Alice", "age": 30}`) is kept distinct from
the raw response part. There is no silent fallback to `ToolOutput` or `PromptedOutput` (no output
tool is registered). `ToolOutput` and `PromptedOutput` are recorded only as alternative framework
strategies, not used here.

Offline this proves that PydanticAI selected NativeOutput, generated the schema, prepared native
output request parameters, passed them to FunctionModel, and parsed and validated the synthetic
response. It does not prove that a real provider supports or followed native JSON-schema output.
Valid JSON alone is not treated as proof that native structured output was requested. The
comparison classifies this as `framework_native_output (pydanticai)` — framework-mediated, NOT the
`native_json_schema` family that the three native SDK lanes occupy.

## 9. Synthetic model profile

`NativeOutput` is grounded in a model profile's `supports_json_schema_output` capability. The probe
supplies that capability EXPLICITLY as a synthetic offline configuration
(`ModelProfile(supports_json_schema_output=True)`), recorded in raw evidence with
`source = "synthetic_offline_configuration"` and `inferred_from_real_provider = false`. Declaring
it explicitly — rather than relying on FunctionModel's permissive default — keeps the evidence
honest: the flag is the probe's own, labelled synthetic. A test asserts the capability was declared
by the probe and not observed from any live provider.

## 10. Deferred-tool handling

For `TOOL-001` a tool is registered as approval-required via
`ApprovalRequiredToolset(FunctionToolset(Tool.from_schema(...)))`, and `DeferredToolRequests` is
included in the run output type. The FunctionModel emits exactly one `ToolCallPart`. The run
terminates with:

```
Agent output = DeferredToolRequests
approval request preserved (tool name, tool-call id, validated arguments, order)
tool body executions = 0
model invocations = 1
second model turn = 0
```

No deferred-tool handler is installed, no approval is supplied, and no tool result is supplied. The
registered tool body raises if executed, so non-execution is enforced. A deferred request is a
terminal state, not a failure, and never classified as successful tool execution. Multiple tool
calls are never inferred as parallel execution.

## 11. Streaming event lifecycle

`STREAM-001` is driven by `agent.run_stream_events()`, which exposes the complete framework event
lifecycle: `PartStartEvent`, `PartDeltaEvent` (text deltas), `PartEndEvent`, `FinalResultEvent`,
and the terminal `AgentRunResultEvent` carrying the final result. Event type, sequence, and text
deltas are preserved. PydanticAI events are treated as framework-owned; where no shared semantic
event fits, they are retained as `framework_extension`, never labelled provider-native. Offline,
the streamed response carries no `finish_reason` (an honest artifact of the FunctionModel stream);
real event delivery and terminal signalling remain `unverified_until_live`.

## 12. Graph-node evidence

`agent.iter()` is exercised as a distinct dimension from `run_stream_events`: it yields the Agent
graph node lifecycle `UserPromptNode -> ModelRequestNode -> CallToolsNode -> End`. For non-stream
fixtures `agent.iter` is the primary driver (it yields both the graph nodes and the final result in
one run); for the stream fixture it is a separate single-request exercise for graph-node evidence.
The distinction is preserved and recorded: `run_stream_events` proves framework stream events plus
the final result; `agent.iter` proves the graph nodes plus the graph execution lifecycle. Neither
run is a retry of the other, and no single API is claimed to prove both dimensions.

## 13. Retry and request-limit ownership

Each retry owner is configured to zero independently and MEASURED, never inferred:

```
output-validation retries = 0   (AgentRetries.output)
tool retries              = 0   (AgentRetries.tools)
per-tool retries          = 0
model-request limit       = 1   (UsageLimits(request_limit=1))
probe retries             = 0   (one primary run per fixture)
harness retries           = 0
subprocess retries        = 0   (max_attempts = 1)
```

Invocation count is read from `RunUsage.requests`. Tests prove that malformed structured output, a
JSON parse failure, and a tool-argument validation failure each raise after exactly one
FunctionModel invocation (no second call), that a deferred TOOL-001 causes no second model turn,
and that an executing tool that would force a second model request is stopped by the one-request
limit with `UsageLimitExceeded`. A successful final result is never hiding an earlier retry (the
per-run request count is 1 in every fixture).

## 14. Usage provenance

Two usage figures are preserved distinctly. The `ModelResponse` usage (a `RequestUsage` injected by
the offline FunctionModel) is synthetic offline evidence, so at the model-response level it is
`fixture_expected`. The Agent run total (`RunUsage`, with `requests` and `tool_calls` counters) is
framework-owned aggregation and is labelled `framework_native` on the result usage record — never
`provider_native`. The two are not merged without provenance. The cache split
(`cache_read`/`cache_write`) is preserved and missing usage stays absent (never coerced to zero).
Real provider usage accuracy is `unverified_until_live`.

## 15. Model identity provenance (P0.6D applied)

The result carries `observed_model_identity` (requested_model / observed_returned_model /
observed_returned_model_source / observed_returned_model_raw_ref / execution_mode /
model_identity_match). The observed returned model is read from PydanticAI `ModelResponse.model_name`.
Offline the FunctionModel exposes a SYNTHETIC `model_name` (`function:offline-synthetic-model`)
distinct from the requested model, so `requested != observed` is recorded
(`model_identity_match=false`), non-failing, with `observed_returned_model_source = fixture_expected`.
A framework-only live source would be `framework_native`, never `provider_native`. The requested
model is never copied into the observed field; there is no canonicalization (no lowercasing, prefix
stripping, snapshot removal, or alias resolution); an absent model stays `unavailable`.

## 16. Error and terminal semantics

Terminal and error states are kept distinct. A successful final output, a `DeferredToolRequests`
terminal (mapped from `finish_reason=tool_call` to the `requires_action` category), a framework
validation error, an output validation error, a tool validation error, a usage-limit error, and an
unexpected-model-behavior error are all representable and observable. PydanticAI's exception
hierarchy (`UnexpectedModelBehavior`, `UsageLimitExceeded`, `ModelHTTPError`, `ModelAPIError`, and
others) is captured with type, module, message, and cause chain. Framework exceptions are never
labelled provider errors, and `DeferredToolRequests` is never classified as a failure. Offline
faults are exercised via validation failure and the one-request limit; real network-mapped provider
exceptions are `unverified_until_live` (no live error fixture is authorized).

## 17. Instrumentation and privacy

Instrumentation is never enabled: `instrument_all` is not called and no `InstrumentationSettings`
are passed. Full `logfire` and the OpenTelemetry SDK/exporter are not installed — only the inert
`logfire-api` and `opentelemetry-api` interface shims are present transitively, so no telemetry can
leave the process. No Pydantic AI Gateway client is constructed and no custom endpoint is
configured. Provider model integrations (openai/anthropic/google) require vendor SDKs absent in the
slim install, so `import pydantic_ai.models.openai` fails — a real provider model cannot be built.
No prompt, response, tool arguments, usage, model identity, or metadata leaves the process, no
credential is required offline, and no secret value is serialized (narrow key redaction, plus a
run-level shape-based secret scan). Tests assert no Logfire export, no OpenTelemetry exporter, no
Gateway client, no unexpected outbound connection, no credential requirement, and no secret
serialization.

## 18. Protocol-neutrality findings

PydanticAI does not reintroduce N-01..N-05:

- N-01 (framework-normalized usage represented as provider-reported): the Agent RunUsage aggregate
  is `framework_native`, never `provider_native`.
- N-02 (provider/framework usage fields dropped by OpenAI-shaped paths): the neutral usage summary
  carries the cache split from RunUsage; no OpenAI-nested path is read.
- N-03 (terminal-state collapse): `observed_terminal_state` stays queryable; the deferred terminal
  is preserved distinctly (`tool_call` -> `requires_action`).
- N-04 (missing or invented provenance): every value uses the central provenance vocabulary; the
  synthetic model profile and offline model identity are labelled `fixture_expected`/synthetic, not
  invented as provider evidence.
- N-05 (requested/returned model conflation): requested and observed are separate fields; the
  synthetic offline mismatch is recorded, not resolved.

Also proven: framework parts are not labelled provider-native; valid JSON alone is not native
structured-output proof; deferred tools are not labelled successful tool execution; multiple tool
calls do not imply parallel execution; missing usage stays absent; unknown events are retained as
`framework_extension`; Agent instructions are not relabelled provider-native system messages. No new
F1 was found: offline shape differences are framework-implementation evidence, and no reproducible
shared-contract loss or false provenance was observed. Any future recurrence involving contract
loss, false provenance, or false equivalence would be a candidate F1.

## 19. Six-lane comparison

The comparison and the neutrality matrix are extended to six lanes: `openai-native`, `langchain`,
`anthropic-native`, `gemini-native`, `litellm-sdk`, `pydantic-ai-agent`. The matrix now carries 18
dimensions: the original 12 (each gaining a `pydantic-ai-agent` entry) plus six PydanticAI-relevant
dimensions — `agent_graph`, `instruction_and_message_parts`, `retry_and_request_limit_ownership`,
`run_level_usage_aggregation`, `instrumentation_and_gateway`, and
`provider_native_evidence_availability`.

The three frameworks are compared without being treated as equivalent: for STR-001 LangChain uses
function-calling, LiteLLM a translated `response_format`, and PydanticAI native-output — three
distinct framework-mediated structured-output mechanisms, none of them provider-native. Only the
three native SDK lanes occupy the `native_json_schema` family. Every report states that this is
implementation-shape evidence only and not live provider semantic evidence.

## 20. Offline limitations

No live evidence exists yet. All P0.7B verification is offline via FunctionModel, which runs the
real Agent graph, message/part model, output-strategy selection, validation, deferred-tool
handling, usage aggregation, and stream events without the network. Output/tool/per-tool retries
are zero and a one-request usage limit is applied; the Pydantic AI Gateway is never used and
Logfire/OpenTelemetry export is never enabled. The streamed response carries no `finish_reason`
offline. The probe emits raw evidence and a minimal manifest only; normalization is a harness stage.

## 21. Live-only unknowns (`unverified_until_live`)

The following require a real provider call and are not settled by offline evidence: real
provider-native request semantics; real provider structured-output adherence to a native JSON
schema; real provider tool-call selection; real provider retry behavior; real provider streaming
behavior and event delivery; real provider usage accuracy; real provider model routing / alias /
snapshot resolution; and real provider error taxonomy. The offline FunctionModel substitutes any
provider, so for this framework lane no provider-native evidence exists offline — every value is
`framework_native` or `fixture_expected`, and provider semantics stay `unverified_until_live`.
