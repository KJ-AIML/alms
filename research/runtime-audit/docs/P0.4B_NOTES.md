# P0.4B OpenAI Live Runner Wiring

Wiring only. **No live provider request was made during P0.4B.** This slice connects the
existing audit harness to the isolated OpenAI native probe so that a future, explicitly
authorized live run can select a bounded configuration and execute one lane over an
approved fixture subset. Every behavior here is proven offline through the probe's mock
mode over a real subprocess boundary, with zero network and zero credential reads.

Scope stayed inside `research/runtime-audit/`. No production ALMS source was changed, no
provider SDK was added to the harness, no ModelRuntime was created, and no generalized
multi-provider runner was built.

## 1. Implemented CLI surface

`alms-audit run` gained bounded-execution selection (existing flags kept, no aliases added):

- `--config` explicit config file (e.g. the first-live override); required for execution.
- `--lane` a single lane id (one lane only for the first-live path).
- `--model` explicit provider model id (no hidden default).
- `--fixtures` comma-separated fixture ids, executed in the order given.
- `--run-id` deterministic run identity.
- `--offline-execute` run the full pipeline through the probe in mock mode (no network,
  no credential). Distinct from a dry-run and from a live run.
- `--live` / `--confirm-live` the live path (fail-closed; not exercised this session).

Default `run` (no execution flag) remains a dry-run: plan plus an immutable manifest, no
subprocess, no calls.

## 2. Run selection behavior

Selection is deterministic and fails closed. The CLI refuses, before any subprocess:

- missing configuration (execution requires `--config`)
- unknown configuration path
- missing or unknown lane
- more than one lane (only one `--lane` is accepted)
- missing model in an execution run
- empty fixture selection
- unknown fixture ids
- duplicate fixture ids
- fixtures ineligible for the lane (a capability the probe does not implement, e.g.
  embeddings or multimodal on the openai-native lane)
- fixtures outside the approved first-live set when the first-live config is used
- live execution without `--confirm-live`
- live execution without a valid budget
- live execution without credential presence
- an expected call count above the call cap, or an upper-bound cost above the hard cap

Fixture order is exactly the requested order and is recorded in the plan, run manifest, and
run summary.

The approved first-live fixture set (`GEN-001, ROLE-001, STR-001, TOOL-001, STREAM-001,
USAGE-001`) is expressed in `configs/first-live.override.toml` under `[live_acceptance]`,
not hardcoded into the generic corpus. Only a config that declares that table restricts
selection; the default config does not.

## 3. Pricing snapshot strategy

Pricing is committed, non-secret config, never fetched at runtime and never silently
updated. `configs/first-live.override.toml` carries a `[[pricing]]` snapshot for the
selected low-cost OpenAI model (`gpt-5.4-nano`, the cheapest GPT-5.4-class model, checked
2026-07-13) with: `model_id`, `price_checked_at`, `input_price_per_million`,
`output_price_per_million`, `estimated_input_tokens_per_call`,
`maximum_output_tokens_per_call`, `maximum_calls`, `pricing_source_note`. Prices are strings
so budget arithmetic is exact `Decimal`, never binary float.

`pricing.gate_cost` computes an upper-bound estimate and fails closed when pricing is
absent, the snapshot model does not match the selected model, the estimate cannot be
computed, the estimate exceeds the hard cap, or the expected calls exceed the call cap. The
estimate is a safety upper bound, not an accounting claim. Actual usage and an estimate
based on reported usage are recorded separately per fixture after execution.

For the six approved fixtures on one lane the planner derives an expected call count of 6
(cap 8), and the upper-bound estimate is about 0.00156 USD, far under the 1.00 USD hard cap.

## 4. Subprocess invocation model

One probe subprocess per fixture. Each invocation receives run id, fixture id, lane id,
explicit model, timeout, maximum output tokens, raw-evidence location, and an execution
mode, via a Probe Process Protocol v0 request JSON. The secret value is never in the
request.

The harness launches the probe through the probe project's **own** locked interpreter
(`probes/openai-native/.venv`), invoked directly as `<probe-venv-python> -m probe
<request.json>`. This keeps the OpenAI SDK isolated to the probe environment; the harness
process never imports it. (A nested `uv run` was intentionally avoided: launched from
inside the harness's own `uv run`, it hangs on Windows; the direct interpreter path is both
faster and hermetic. It fails closed with guidance if the probe env is not synced.)

For offline runs the child receives `ALMS_PROBE_BLOCK_NETWORK=1`, which installs a
process-level socket tripwire in the probe before any client is constructed. A mock run that
tried to open a socket would fail loudly; this does not rely on the absence of a credential.

## 5. Evidence transaction sequence

Per fixture:

1. build and validate the probe request; write it.
2. launch the probe subprocess; capture stdout, stderr, exit code, duration.
3. the probe writes **raw** artifacts first (request, native response or event stream,
   probe stdout/stderr, a probe-response manifest) into the fixture's `raw/` directory.
4. the harness verifies the raw request and response artifacts exist **before** any
   interpretation.
5. validate the probe-response manifest against its schema.
6. normalize the raw evidence into a transcript (separate step, harness side).
7. build a schema-valid result record.
8. append the fixture's terminal status to the run summary.

Raw artifacts are never rewritten after they are finalized. Normalized and result records
are written only after the raw evidence is confirmed present.

## 6. Partial failure policy

One fixture's failure never erases earlier fixtures' evidence. Terminal states are distinct:
provider success (`PASS`), provider extension or refusal (`PASS_WITH_EXTENSION`, with a
`provider_refusal` note for refusals), provider error (`ERROR_RUNTIME`), probe blocked
(`BLOCKED_CONFIGURATION`), probe process error or timeout (`ERROR_RUNTIME` with a diagnostic
note), invalid probe response or missing raw artifact or normalization failure
(`INCONCLUSIVE`). Nothing is auto-retried. The run summary lists every selected fixture with
its status. A detected secret leak or an attempt to overwrite an existing run id is a hard
safety failure that aborts.

## 7. Normalization boundary

Normalization stays a harness concern. The probe preserves native semantics; the harness
normalizer maps them into audit vocabulary (text deltas, tool-call events, structured
output, usage, response completion, error) and preserves any unmapped native event as a
`provider_extension` rather than discarding it. Unknown event payloads are kept. In the
offline simulation, STREAM-001 legitimately yields `PASS_WITH_EXTENSION` because the mock
stream includes a native `output_item.added` (message) event that the normalizer preserves
as a provider extension; this is faithful behavior, not a wiring defect.

## 8. Usage and cost handling

Provider-reported input/output/total usage is preserved when present. Missing usage stays
absent (every token field null, provenance `absent`); it is never coerced to zero.
`cost_reported` is null (the provider does not report a dollar cost); `cost_estimated` is a
`Decimal`-computed estimate from the pricing snapshot and the reported usage, kept distinct
from the plan's upper-bound estimate and from any billed cost.

## 9. Secret-handling model

Credential state is presence-only everywhere outside the probe child process. The value
never appears in CLI output, plan, run manifest, probe request, stdout, stderr, raw request,
normalized transcript, result record, or run summary. The probe redacts raw artifacts before
writing them, and a final run-level secret scan runs before the run is declared complete; any
hit is a hard abort. Tests use only a synthetic credential and assert it never appears in any
artifact. In the live path the credential-presence gate refuses before any subprocess when
the key is absent, so a live run cannot even launch without a real credential present.

## 10. Offline acceptance simulation

The full first-live command was run offline through the real CLI and real subprocess:

```
alms-audit run \
  --config ../configs/first-live.override.toml \
  --lane openai-native \
  --model gpt-5.4-nano \
  --fixtures GEN-001,ROLE-001,STR-001,TOOL-001,STREAM-001,USAGE-001 \
  --offline-execute \
  --run-id <id>
```

All six fixtures executed end to end (CLI -> planner -> runner -> real subprocess -> probe
mock -> raw capture -> normalization -> result records -> run summary). Expected provider
network calls: 0. Actual OpenAI SDK requests: 0. Every probe response is labelled
`offline_mock`; the run manifest records `execution_mode = offline`. Mock output is never
labelled as live evidence.

## 11. Remaining live-only unknowns

Documented SDK/model support is not proof. The following remain `unverified_until_live` and
can only be confirmed by an authorized live run: native structured-output strict-mode
behavior, true function tool-call semantics and argument fidelity, real streaming event
ordering and terminal state, provider-reported usage shape and values, and real
single-attempt (no-retry) behavior. Offline evidence exercises the pipeline and the shapes
the mock models, not the provider's actual behavior.
